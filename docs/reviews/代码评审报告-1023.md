## 1. P0 — 用户直接可见的错误结果

> ✅ **P0-1 / P0-2 已于 2026-10-23 批次 1 修复**（见 §0.5）。下面保留原始描述与证据。

### P0-1 矩形族手柄拖拽：对象会**飞离光标**（位移二次累加）🔴 最严重

**位置**：`Sources/AnnotationView.swift:774-775`

```swift
let worldCenter = CGPoint(x: startCenter.x + rotatedLocal.x,
                          y: startCenter.y + rotatedLocal.y)
obj.move(by: CGVector(dx: worldCenter.x - startCenter.x,   // ← 相对「起始中心」的位移
                      dy: worldCenter.y - startCenter.y))
```

`obj.move(by:)` 是**相对增量**（`Models.swift:2320-2323`：`center.x += delta.dx`），
但这里的 delta 是拿「worldCenter − **startCenter**」算的，而 `startCenter` 是
**mouseDown 时**捕获的起点。于是第 2 个 `mouseDragged` 起，每次都把「已经生效过的位移」
再加一遍：

- 正确：`center = startCenter + (worldCenter − startCenter)`
- 实际：`center = Σ(worldCenterᵢ − startCenter)` → **二次增长**

**实测**（聚光灯 200×200，中心 (300,200)，拖右边手柄，每次 +10pt）：

| 拖拽事件数 | 期望中心.x | 实测中心.x | 宽度 |
|---|---|---|---|
| 1 | 315 | 315 ✅ | 230 ✅ |
| 10 | 350 | **575** ❌ | 300 ✅ |
| 30 | 450 | **2625** ❌ | 500 ✅ |

宽度始终正确（宽度只依赖光标相对 `startCenter` 的关系），但**中心**按 `5·k(k+1)/2` 膨胀。
30 个事件后本该在 x=450 的矩形跑到 x=2625 —— **直接飞出画布**。
「拖右边手柄、另一边锚定不动」这条契约（`AnnotationView.swift:730-733` 的注释明写）
在**第二个事件**就失效了。

**为什么现有回归没抓到**：`probes/resize_handle_probe.swift` 每一节都只发**一个**
`mouseDragged`。真实拖拽是「按下 → 拖 N 次 → 松手」，两条路径不是一回事。

**旁证**：Esc 取消路径算的是同一个移动，但**算对了**（`AnnotationView.swift:1143-1145`
用 `delta = startCenter.x - obj.center.x`，相对**当前**中心），恰好证明拖拽路径是异常项。

**修法**：把中心写成绝对值，或相对当前中心算增量：

```swift
obj.move(by: CGVector(dx: worldCenter.x - obj.center.x,
                      dy: worldCenter.y - obj.center.y))
```

### P0-2 `.resize` 撤销只还原尺寸，**不还原位置**

> ✅ **已修复**（2026-10-23 批次 1）。`UndoAction.resize` 现在带 `oldCenter`/`newCenter`。

**位置**：`Sources/Models.swift:443`、`Sources/AnnotationView+UndoRedo.swift:63-68`

```swift
case resize(colorKey: UInt32, oldSize: CGSize, newSize: CGSize)   // ← 没有中心
```

但手柄调整在改尺寸的同时**也会移动中心**（锚点模型：新中心 = 新包围盒中心，
`AnnotationView.swift:766-775`）。`.resizing` 状态里明明存着 `startCenter`，
撤销记录却没带。

**实测**：拖右边手柄 +30（宽 200→230，中心 300→315）后按 ⌘Z → 宽变回 200 ✅，
**中心停在 315** ❌（应为 300）。拖角手柄、矩形族同样中招。

README:63-65 承诺「Esc 中途取消、⌘Z 可撤销」，`resize_handle_probe.swift:73-74`
只断言了宽高 —— 缺口正在这里。

### P0-3 OCR 结果面板：选中的文字**高亮到错误的框**

**位置**：`Sources/OCR/OCRResultWindow.swift:35-42`、`:112`、`:174`

```swift
for item in items { ... }                    // :37  按 Vision 原始顺序建区间
textView.string = TextRecognizer.joinedText(items)   // :112  按**阅读顺序**显示
onHighlightChanged?(touched.map { items[$0].box })    // :174  按原始顺序回查框
```

`joinedText` 内部走 `TextRecognizer.readingOrder`（重新排序），而 `blockRanges`
按 Vision 的原始数组序建立。两者不一致时（Vision 不保证返回阅读顺序，是常态），
区间下标与框就**错位**了。

**实测**（Vision 返回 `["RIGHT","LEFT"]`，同一行）：面板显示 `LEFT | RIGHT`，
选中 LEFT 却高亮出 RIGHT 的框。

面板存在的意义就是「这段文字来自图像的哪里」，错了之后这个反馈是**反向误导**的。

## 4. P2 — 体验缺陷与边界错误

1. **窗口选择模式的滚轮选区被下一次鼠标移动重置** —— `refreshHighlight` 每次都
   `candidateIndex = 0`，鼠标一动就跳回最前窗口（`WindowPickOverlay.swift:150-164`）。
2. **`nearestWithin` 用 `best == value` 当哨兵** —— 恰好对齐时会被后面的候选顶掉，
   吸到错误的窗口边（`WindowPickSupport.swift:99-105`，实测 `nearestWithin(100,[100,105]) = 105`）。
3. **历史窗口在主线程同步生成 30 张缩略图** —— 打开即卡顿。**注**：走的是
   `CGImageSourceCreateThumbnailAtIndex`（320px），**不是全尺寸解码**（`CaptureHistory.swift:68-90`），
   卡顿量级比原先估计的小；仍建议挪后台 + `NSCache`（`HistoryWindow.swift:129`）。
4. **更新提示每次启动都弹** —— 没有"已通知版本"状态（`AppDelegate.swift:52-56`、`:177-181`）。
5. **feed URL 输入框存在一条丢失缝** —— `target`/`action` 已覆盖失焦提交
   （`SettingsWindow.swift:274-275`），**唯一漏洞是「编辑中直接点关窗」** → 补一条 `windowWillClose` 读回即可。
6. **`LaunchAtLogin` 把 `.requiresApproval` 当成"未启用"** —— 复选框显示关闭，
   再点一次会重复 `register()`（`LaunchAtLogin.swift:49-51`、`SettingsWindow.swift:582`）。
7. **历史索引写失败被 `try?` 吞掉** —— 磁盘满时内存与磁盘索引静默分叉（`CaptureHistory.swift:251-257`）。
8. **选区吸附清单在冻帧之后才取** —— 冻结只锁住了图像、没锁住布局，
   期间出现的窗口会以「当前位置」画高亮，与冻帧内容错位（`RegionSelectionWindow.swift:122-136`）。
9. **纯点击选区零反馈** —— 拖小了会哔，纯点击（最常见的"选太小"）一声不吭（`RegionSelectionWindow.swift:285-293`）。
10. **macOS 14.x 路径每屏各查一次 `SCShareableContent`** —— 三屏冻帧来自三个不同时刻，
    且冻结耗时 ×3（`CaptureProviderSCK.swift:32-33`）。
11. **孤儿 PNG 累积** —— 图片先写、索引后写，中间崩溃则该文件永远不被回收（`CaptureHistory.swift:131-149`）。

## 5. P3 — 低影响 / 需运行时确认

- 贴图窗口滚轮缩放**不**更新 alpha mask —— 复核后确认**这是设计正确、不是缺陷**：
  mask 建在图像空间，`isPassThrough` 按**归一化坐标**采样（`PinWindow.swift:353-368`），
  缩放天然不变。原报告此项为误报，已撤。
- `findNearestSnapPoint` 遍历 Dictionary，等距时胜者不稳定 → 指示器可能闪烁（`AnnotationView+Snapping.swift:18-27`）
- `HitTestBuffer` 用 `Int(size.width)` 截断 → 右/上边缘亚点条带无命中像素（`HitTestBuffer.swift:15-16`）
- `Int(point.x)` 向零截断 → x = −0.3 会命中第 0 列（`HitTestBuffer.swift:71-72`）
- 撤销栈无深度上限（`AnnotationView.swift:119-120`）
- 橡皮擦按 9 个离散点采样而非实心圆盘（`AnnotationView.swift:1275-1290`）
- `erase(at:)` 每删一个对象就整幅重绘 Layer B（`AnnotationView.swift:1298`）
- 附着存的是**归一化周长参数** → 父对象被**缩放**时锚点会沿周长滑动，而不是停在原位（`AnnotationView+Attachments.swift:54-55`）
- 窗口选择的滚轮方向注释与实现相反（`WindowPickOverlay.swift:116-121`）—— 代码是对的，注释错了
- 更新清单无签名/校验，默认源在**可变的 master 分支**上（设计层面风险）

## 6. 确认**没有**问题的部分（避免下一轮重复排查）

这些是本轮专门验证过、确认正确的：

- **命中层与可见层无倍率错配** —— Layer B 按画布**点**分辨率建（`HitTestBuffer(size: image.size)`），
  Layer A 在设备倍率下光栅化但采样始终在点空间，`fitScale < 1` 时两层一起缩放。**不存在**经典的 backing-scale mismatch。
- **`pickColorKey` 的 Y 翻转正确** —— 位图 row 0 在顶、CG 原点在底 → `height-1-y` 正确。
- **颜色 key 编码可靠** —— 单调唯一、0 号保留给背景、关闭抗锯齿且逐对象 `save/restoreGState`，
  不会有抗锯齿混色产生外来 key。
- **`ScreenGeometry` 的 Y 翻转与 AppKit↔Quartz 换算正确**，含副屏在主屏上方/左方、负原点的情况。
- **覆盖层不是倒的** —— 非翻转 AppKit 视图里 `ctx.draw(frozen, in: bounds)` 方向正确。

### 9.2 不同意：P1-6 贴图泄漏**属实**，不应列入「不修」

计划 §1.3 / §9.3 判「不成立、不修」，依据是 `PinWindow.close()` override 先
`PinManager.unregister(self)` 摘掉数组里的强引用。

**这个前提本身没错，但它只覆盖了 PinManager 的数组，覆盖不到 AppKit 的窗口列表。**
真正留住窗口的是 `NSApp.windows` —— 而 `isReleasedWhenClosed = false`
（`PinWindow.swift:33`）意味着 AppKit 在 close 后**仍持有**这个窗口。

我写了 `probes/pin_lifetime_probe.swift` 实测（链接真实 `PinWindow` + `PinManager`）：

| 场景 | `NSApp.windows` 净增 |
|---|---|
| 现状（`isReleasedWhenClosed = false`）：10 次「贴图→关闭」 | **+10**（全部残留） |
| 走真实生产路径 `PinManager.shared.pin()`：5 次 | **+5**（同时 `PinManager.count` 正确归 0，证明 `unregister` 确实执行了） |
| 改成 `isReleasedWhenClosed = true`：10 次 | **0** ✅ |

即：泄漏确实存在，且**修法就是 `isReleasedWhenClosed = true`** —— `close()` override 里
`unregister` 在 `super.close()` **之前**执行，PinManager 的引用先摘掉，AppKit 随后才释放，
顺序是安全的。

**判据说明**：本探针以 `NSApp.windows` 计数为准，不用 weak 引用 ——
`NSWindow.close()` 会把窗口放进当前 autorelease pool，探针没有 run loop，池在程序结束前
不排空，weak 恒非 nil（假信号）；手工开 pool 排空又会让 AppKit 在无 run loop 时释放
仍登记着的窗口而段错误。

**结论：P1-6 应移回修复列表。** 计划 §9.3 提到的「可选加一个 pin 释放探针防回归」
——探针已在本报告 §3 列出，修完即可注册成常驻回归。

### 9.3 对计划 §5.1（P1-1 修法）的一个必须注意的实现约束

计划建议新增 `func canScale(by factor: CGFloat) -> Bool { true }` 并让有钳制的形状各自覆写。
**它必须作为协议要求声明在 `AnnotationObject` 的协议体里**，默认实现放 extension。
若只写成 extension 成员（协议体里不声明），经 `any AnnotationObject` 调用时会**绕过覆写**、
永远命中默认的 `true` —— 修复静默失效。

本仓库已经踩过同一个坑并写在注释里（`Sources/Tools/AnnotationToolHandler.swift:66-72`：
「Swift 的协议扩展方法不参与存在体动态分发…… 一笔画完对象永远是 nil」）。

两个变体的实测：

```
canScale 作为协议要求 → 经 any Shape 调用 → false ✅（覆写生效）
canScale 仅作扩展成员 → 经 any Shape 调用 → true  ❌（覆写被绕过）
```

`AnnotationView.swift:700-712` 的调用点持有的是 `any AnnotationObject`，所以必须走协议要求那条路。
