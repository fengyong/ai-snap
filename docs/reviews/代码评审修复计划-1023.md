### 3.1 P0-1 位移二次累加

**位置**:`Sources/AnnotationView.swift:774-775`

**根因**:`.resizing` 状态在 mouseDown 捕获 `startCenter` 后**不再更新**(mouseDragged 里没有
state 重赋值,这是刻意设计——span 全部从原始锚点算,本身没错)。但写中心时:

```swift
obj.move(by: CGVector(dx: worldCenter.x - startCenter.x,   // 相对「起始中心」
                      dy: worldCenter.y - startCenter.y))
```

`move(by:)` 是相对当前中心的增量(`Models.swift:2320-2323`)。第 1 个事件碰巧正确
(当前中心 == startCenter),第 2 个事件起每个事件都把「相对起始中心的全量位移」
再加一遍 → 中心按 5·k(k+1)/2 二次膨胀(实测 30 个事件后 center.x = 2625)。
宽度因为走 `setSize`(绝对赋值)始终正确。Esc 路径(`:1143-1145`)用相对**当前**中心的
增量,是对的——这也印证了拖拽路径是异常项。

**修复**:增量改为相对当前中心(目标中心是绝对的,每次事件收敛到同一目标):

```swift
obj.move(by: CGVector(dx: worldCenter.x - obj.center.x,
                      dy: worldCenter.y - obj.center.y))
```

单事件、多事件、旋转后的矩形族全部由「绝对目标 + 相对写入」覆盖,不再依赖历史。
(不建议直接 `obj.center = worldCenter`:保持与代码库 `move(by:)` 风格一致。)

### 3.2 P0-2 `.resize` 撤销不还原中心

**位置**:`Sources/Models.swift:443`(枚举)、`Sources/AnnotationView.swift:923-932`(记账)、
`Sources/AnnotationView+UndoRedo.swift:63-68 / 147-152`(undo/redo)

**根因**:手柄调整在改尺寸的同时按锚点模型移动中心,撤销记录却只带
`oldSize/newSize`。全库 `.resize` 构造点只有一个(mouseUp :926),枚举扩展影响面封闭。

**修复**:

1. 枚举带上中心(`UndoAction.resize` 增加两个关联值):

```swift
case resize(colorKey: UInt32, oldSize: CGSize, newSize: CGSize,
            oldCenter: CGPoint, newCenter: CGPoint)
```

2. mouseUp 记账(:926,`startCenter` 目前被 `_` 丢弃,改为解构使用):

```swift
undoStack.append(.resize(colorKey: colorKey,
                         oldSize: CGSize(width: startWidth, height: startHeight),
                         newSize: CGSize(width: obj.width, height: obj.height),
                         oldCenter: startCenter,
                         newCenter: obj.center))
```

3. undo(:63-68)在 `setSize(old)` 后把中心也回去;redo(:147-152)对称:

```swift
obj.setSize(width: oldSize.width, height: oldSize.height)
obj.move(by: CGVector(dx: oldCenter.x - obj.center.x, dy: oldCenter.y - obj.center.y))
```

(redo 同理写 `newSize/newCenter`。)`updateAttachedArrows` 两处已调用,保留。)

**兼容性**:`resize_handle_probe.swift:115-119` 的 `if case .resize = undo` 模式匹配
不受新增关联值影响;`probes/resize_undo_probe` 本来就断言中心,修好后应全绿。

### 4.1 P0-3 OCR 结果面板高亮错框

**位置**:`Sources/OCR/OCRResultWindow.swift:37-42`(区间按原始序)、`:112`(显示按阅读序)、
`:170-174`(按原始序回查框);调用方 `Sources/AnnotationWindow.swift:1016→1033` 直接传
Vision 原始结果,未排序。

**根因**:`TextRecognizer.joinedText` 内部走 `readingOrder` 重排,而 `blockRanges` 与
`items[$0].box` 都按传入数组的原始下标。`TextRecognizer.swift:44-45` 自己的注释就写明
Vision 返回顺序 ≠ 阅读顺序 → 错位是常态不是边角。

**修复**(推荐在面板内归一,调用方不动):`OCRResultWindow.init` 一进来先

```swift
self.items = TextRecognizer.readingOrder(items)
```

`blockRanges`、`joinedText(items)`(对已排序输入幂等)、`items[$0].box` 三者随即同序。
空选区「全部高亮」是全量 box,与顺序无关,不受影响。
`AnnotationWindow.presentOCRResults:1049` 的初始全量高亮同样不受影响。

**验证**:ocr_probe 保持绿;真机:截一张左右分栏、右侧内容在前的图(或手动构造两段
文字,让 Vision 先返回右边的),面板里选第一行 → 画布高亮的必须是第一行显示文字的框。

### 4.2 P0-4 打码预览与最终对象不一致

**位置**:`Sources/Tools/RedactionToolHandlers.swift:37-48`

**根因**:`makeObject` 处理了 `drawingFromCenter`(:21-26,起点吸附到角点时以起点为中心、
尺寸翻倍),`drawPreview` 无条件 `RedactionShape(from:to:)`。对照
`ShapeToolHandlers.swift:41-53`(矩形)、`:101-144`(椭圆,makeObject/drawPreview 共用
`makeShape`)——只有打码漏了。对打码这是隐私级错误:用户看到的预览是一小块,松手打码的
是另一块大一倍的区域。

**修复**(照椭圆 handler 的模式,抽公共构造保证两条路径永远同构):

```swift
func drawPreview(from start: CGPoint, to end: CGPoint,
                 tool: DrawingTool, in ctx: CGContext, context: ToolContext) {
    guard let preview = makeShape(from: start, to: end, style(for: tool), context: context) else { return }
    preview.draw(in: ctx)
}

private func makeShape(from start: CGPoint, to end: CGPoint, _ style: RedactionStyle?,
                      context: ToolContext) -> RedactionShape? {
    guard let style = style else { return nil }
    if context.drawingFromCenter {
        return RedactionShape(center: start,
                              width: max(abs(end.x - start.x) * 2, 6),
                              height: max(abs(end.y - start.y) * 2, 6),
                              style: style, hitTestColorKey: 0)
    }
    return RedactionShape(from: start, to: end, style: style, hitTestColorKey: 0)
}
```

`makeObject` 改为复用 `makeShape`(传 `context.colorKey` 版本需另加参数或保持
`hitTestColorKey` 由调用方覆盖——实现时以「两路径共用同一构造」为验收标准)。

**顺手排查**:`grep -n drawingFromCenter Sources/Tools/*.swift`,确认其余 handler 的
makeObject/drawPreview 对 `drawingFromCenter` 处理对称(Spotlight 两侧都不处理,是对称
的,不算)。

**验证**:redaction_probe 保持绿;真机:悬停到某对象角点出现吸附十字 → 从角点拖出打码
→ 拖拽过程中的预览框与松手后的打码区域必须完全重合。

## 5. 批次 3 — 撤销语义收尾(P1-1 + P1-2)

### 5.1 P1-1 `.scale` 撤销在下限处过冲(含 Esc 同根)

**位置**:`Sources/AnnotationView.swift:697-713`(手势)、`:913`(记账)、
`Sources/AnnotationView+UndoRedo.swift:56-61`(undo)、`AnnotationView.swift:1126-1131`
(Esc 回退,同根);`Sources/Models.swift:681-684`(`scaledExtent` 钳制)。

**根因**:撤销记录的是**请求倍率** `scaleStartFactor`(每事件 `*= factor`,钳制发生
在 `scale(by:)` 内部但不反映到累计值)。200 → ×0.01 实际被夹到 4,⌘Z 乘回 100 → 400。
Esc 取消路径同样用 `1/scaleStartFactor`,同根过冲。

**为什么不建议「记录实际生效倍率」**:钳制是**按维**的——w=200/h=50 的对象缩到下限时
两维的实际倍率不同(0.02 vs 0.08),单一标量无论记哪个都无法精确还原两维。

**修复(推荐:手势端门控,让「请求 == 生效」恒成立)**:

1. 给形状加可缩放判定(默认放行,有钳制的形状各自覆写):

```swift
// AnnotationObject 扩展(或协议方法),默认实现:
func canScale(by factor: CGFloat) -> Bool { true }
```

- 矩形族(RectShape 等,`Models.swift:1125-1129`):
  `RectResizable.scaledExtent(width, by: f) == width * f && 同 height`
  (上推永远过 `scaledExtent`,只有触下限才 false);
- 箭头(`Models.swift:954` 的 `length >= minimumExtent || factor >= 1` 守卫):
  把同一条件放进 `canScale`;
- 其余形状无钳制,吃默认值。

2. `mouseDragged` 的 `.scaling` 分支(:700-712)把「应用缩放」与「累计倍率」绑定:

```swift
if obj.canScale(by: factor) {
    obj.scale(by: factor)
    scaleStartFactor *= factor
    state = .scaling(colorKey: colorKey, lastDistance: currentDist)
}
```

(现有 `minDim * factor > 0.5 || factor >= 1` 兜底守卫保留为廉价前置。)

**效果**:到达下限后继续拖不再生效(与主流编辑器一致),请求倍率与实际严格相等 →
undo 的 `1/factor` 与 Esc 回退天然精确,`scaledExtent`「只止损不抬高」语义不破坏。
**注意**:这会让「缩到下限后继续拖、松手、⌘Z」还原到下限前最后生效的尺寸,
行为上等价于「缩到下限的那一下就是最后一次缩放」,符合直觉。

**验证**:resize_undo_probe §5(正常缩放撤销,保持绿)、§6(下限过冲,由失败转通过,
断言撤销后回到 200)。真机:Shift 拖到缩不动 → ⌘Z 完整复原;拖到一半按 Esc 同样复原。

### 5.2 P1-2 首次文字编辑 ⌘Z 留下隐形空对象

**位置**:`Sources/AnnotationView+TextEditing.swift:64-69`(记账)、
`Sources/AnnotationView+UndoRedo.swift:70-75`(undo 只回 text)。

**根因**(核实后):文字创建时撤销栈为 `[.add, .editText(previous: "")]`。一次 ⌘Z 只回
`.editText` → text 归空、对象仍在,空串 contentSize 实测 **8×32**(行高 24+padding 8),
命中区外扩 6pt/边后 **20×44pt** 隐形可点(报告写 8×8 / 20×20,数字偏小,问题只重不轻)。

**修复(最小改动,利用对象是引用类型这一事实)**:创建态的首编**不再单独记
`.editText`** —— `.add` 的 undo 本来就摘除整个对象,而 `.add` 记录持有同一实例,
redo 装回时自然带着已输入的文字:

```swift
if commit, !newText.isEmpty {
    shape.text = newText
    // 创建态首编不记 .editText:.add 的 undo/redo 以整个对象为粒度,
    // 实例引用使 redo 自动带回已输入文字;单独记账会留下「撤不掉的空壳」中间态
    if newText != originalText, !originalText.isEmpty {
        undoStack.append(.editText(colorKey: key, previous: originalText))
        redoStack.removeAll()
    }
}
```

语义推演:创建→输入 A→⌘Z = 对象整个消失(一步到位,正是用户预期);⇧⌘Z = 带着 A
回来;再编辑 B 后栈为 `[.add, .editText(prev A)]`,行为与现在一致。空提交回滚分支
(:70-79)不动。

**可选加固**(建议做,杀掉整类问题):`TextShape` 的 drawHitTest 对 `text.isEmpty`
直接不画命中块——空文字对象从此物理不可选中。

**验证**:text_undo_probe(9 通过 1 失败 → 10 通过 0 失败)。真机:点文字工具 → 输入
→ Esc 退出编辑 → ⌘Z 一次,画布上点原位置不应再选中任何东西;⇧⌘Z 文字带内容回来。
