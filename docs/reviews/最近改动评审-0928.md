## 一、merge `6d17314`（`-s ours`）

| 断言 | 证据 |
|---|---|
| 相对第一父**一行代码都没取** | `git diff 6d17314^1 6d17314` 输出为空 |
| 树**逐字节相同** | 两边 tree hash 都是 `e1dd98371e173a8667fe07ba11829d5cf962b10e` |
| A 区历史确已成为 master 祖先 | `7172e73` / `d8d16d2` / `b59086f` 的 `merge-base --is-ancestor` 全部通过 |
| 第二父是 A 的分支 | `6d17314^2` = `b59086f`（`origin/review-fixes`） |
| A 的分支已无独有提交 | `git rev-list --count HEAD..origin/review-fixes` = 0；`git merge-base HEAD origin/review-fixes` = `b59086f` |

**merge 本身没问题，但它埋了一串长期陷阱**（这是本次复核里最该被记住的部分）：

1. **A 的代码再也不能用普通 merge 取回。** A 的提交被声明为"已并入"却一行未取，于是：
   - `git merge origin/review-fixes` → 只会回 "Already up to date"；
   - 从该分支开的 PR → GitHub 显示 **no changes**（三点比较 `HEAD...origin/review-fixes` 为空，
     而两点比较 `HEAD..origin/review-fixes` 是 **116 files, 6414 insertions, 15339 deletions**）；
   - **`git revert -m 1 6d17314` 也是空操作**（该 merge 相对第一父本来就没有 diff）——
     连"反悔"的常规退路都不通；
   - 只剩 `cherry-pick` / `checkout <branch> -- <paths>` / `-X theirs` 可取；
   - **最容易发生的失败模式**：后来者看到 "Already up to date"，以为 A 的修复已经在 master 里。
2. **`git bisect` 会挑到从未发布过的树。** `7172e73`/`d8d16d2`/`b59086f` 都在 `git rev-list HEAD`
   里，但它们的 `Sources/` 是**另一套架构**（8 个文件 vs 40 个）—— 二分结果没有意义。
   本仓库以后二分必须带 `--first-parent`。
3. **历史检索同理**：`git log -S` / `-G` / `--all` 会指向从未在 master 存在过的 A 代码。
   建议把「历史检索默认 `--first-parent`」写进文档。
4. **决策只存在于 commit message**：`docs/` 里没有记录，`origin/review-fixes` 分支还挂着。
   建议补一条决策记录，并把分支改名归档或删掉。
5. 正面：树没变，对**代码**零风险。若目的只是保留 A 的历史以备挑拣，**打 tag 比 `-s ours` 安全**。

## 二、确认并修复的缺陷

### 2.1 短箭头的箭杆被画到**起点的反方向**（`d71f784` 引入｜第一轮发现）

`Sources/Models.swift` 的 `drawArrow`：实心头部的箭杆回缩量取 `headLength * 0.85`，
而 `headLength = max(style.headLength, lineWidth * 3.2)` 在线宽 15 时是 **48** —— 回缩 **40.8pt**。
**任何比 40.8pt 短的箭头**，`endPoint - 回缩量` 会落到起点**反方向**，箭杆倒着画出来，
在三角形头后面露出一截圆头。

像素实测（2x 画布）：

| 箭头 | 实测最左墨迹 | 几何容许的最左 | 结论 |
|---|---|---|---|
| 短箭头 20pt | 443 | 456.9 | ❌ 多出 14px |
| 长箭头 350pt（**对照**） | 85 | 85.0 | ✅ 吻合 |

**判别力**：退回旧写法后**恰好只有**「短箭头」那条失败，长箭头对照仍通过。
**修复**：回缩量加"不超过箭杆长度"的上限；整根箭杆都藏在头部里时不画箭杆。

### 2.2 restyle 的重做（⇧⌘Z）**完全失效**（`833b024` 引入｜两轮**各自独立**发现）

`Sources/AnnotationView+UndoRedo.swift` 的 `undo()` 分支，在**已经把颜色改回旧值之后**
才去读 `obj.color` 构造 redo 记录，于是记录里 `newColor == oldColor`、新旧线宽也相等 ——
重做成了空操作。

实测（选中矩形 → 换蓝 → 线宽 24 → 撤销×2 → 重做×2）：

| 步骤 | 期望 | 实测（修复前） |
|---|---|---|
| 重做换色 | 蓝 1.00 | 蓝 **0.24**（还是红） ❌ |
| 重做改线宽 | 24 | **8** ❌ |

**判别力**：退回后**恰好只有**这两条新断言失败，原有 5 条 restyle 断言**仍全绿** ——
也就是说**原探针根本抓不到它**：第 8 节只测了撤销、**从没测过重做**。
**修复**：redo 记录原样沿用传进来的 `newColor` / `newLineWidth`。
（同文件 `.move`/`.rotate`/`.scale` 都用绑定参数、`.editText` 先取 `current` 再改，
模式本来是对的 —— 只有 `.restyle` 写反了，不是系统性问题。）

### 2.3 权限兜底把"没有权限"判成"有权限"（`833b024` 引入｜独立评审发现，**第一轮复现并确认**）

**这一条是本次最严重的**：它让权限门形同删除。第一轮只把它列为"未能验证的怀疑"
（本机进程都已授权，兜底分支根本不会被执行）；独立评审用
**`launchctl submit` 换一个 TCC 身份**跑同一个二进制，绕开了这个限制。复现结果：

| 运行方式 | `CGPreflightScreenCaptureAccess()` | `canCaptureRealPixels()`（旧判据） | 判定 |
|---|---|---|---|
| 直接跑（已授权） | `true` | `true` | ✅ |
| 经 `launchctl`（无授权） | **`false`** | **`true`** | ❌ **误判为有权限** |

无权限那次的 2×2 探测像素是 `(45,45,50,255)` —— 四个像素一模一样，**那是壁纸**。
根因：**没有权限时 `CGWindowListCreateImage` 依然返回一张非 nil、完全不透明的桌面图**，
于是"有没有非透明像素"这个判据**恒为真**。后果：应用不再弹带「打开系统设置」深链的
权限引导，用户截出壁纸/黑图且**没有任何解释**。

**修复**：改用 ScreenCaptureKit 的**权限专属信号**。实测（同一二进制、两种身份）：

| 运行方式 | `SCShareableContent` |
|---|---|
| 有权限 | 成功（31 个窗口） |
| 无权限 | 抛 `SCStreamErrorDomain Code=-3801`「用户拒绝了…TCC」 |

`canQueryShareableContent()` 用信号量把 async API 包成同步（两个调用点都是同步 `guard`），
**任何失败都按无权限处理**（fail-closed）。反方向不可能出错：只有 SCK **成功**才判 true，
而成功本身就等于实时 TCC 说"允许"。顺带把已经迁走的 deprecated `CGWindowListCreateImage`
从 `AppDelegate` 清掉了。

**新增 `probes/permission_probe.swift`**：它会用 `launchctl` 把**自己**再起一份来构造
"无授权身份"样本 —— 进程内怎么测都测不到这一支，这是唯一能自动验到它的姿势。

> **给以后写探针的人的坑**：子进程的**实时**权限会随"谁把它提交给 launchd"而变 ——
> 经 bash 提交时 SCK 稳定报无权限，经 `Process` 从探针里提交时却报**有**权限
> （TCC 归属认定，环境里带着 `__CFBundleIdentifier=…`）。所以：
> `preflight`（读缓存）与 SCK（读实时）**可以不一致**，而"preflight 说没有、实时说有"
> 恰恰是兜底该救的假阴性 —— **不要断言两者相等**。能判别的性质是
> 「实时无权限 ⇒ 判定必须无权限」；SCK 抖动只会让判定偏保守（多弹一次引导），是安全方向。

### 2.4 线宽滑杆一次拖拽塞进几十条撤销（`833b024` 引入｜独立评审发现）

`NSSlider` 连续发 action，每个值变化都 push 一条撤销。实测：拖 15→30 发出 **61 次**
action → **61 条**撤销记录，按一次 ⌘Z 只退回 0.25px。

**修复**：新增 `GestureReportingSlider`（重写 `mouseDown` 包住整段拖拽 ——
`super.mouseDown` 内部跑到鼠标松开，调用前后正好是两端），拖拽期间实时改但**不**记撤销，
松手时把"起点 → 终点"合成**一条**。键盘方向键 / 点击轨道跳档仍是一档一条。

**判别力**：退回后**恰好只有**那两条滑杆断言失败（`0 → 60`、`0 → 61`）。

### 2.5 短粗箭头的可见头部落在 Option/Shift 门控之外（`d71f784` 引入｜独立评审发现）

头部长度随线宽放大（线宽 30 → 96pt），而 `Arrow.boundingBox` 的 padding 仍用**未放大**的
`style.headLength`（14）—— 可见头部有一圈落在包围盒之外，**按在看得见的头上却转不动它**。

**修复**：padding 改用 `Self.headLength(for:lineWidth:)`。
**判别力**：退回后恰好只有「按在可见头部上 Option 拖拽能旋转」失败
（抓取点 `(232,200)` 是刻意挑的有判别力位置：在三角头后缘 `x=227` 之内、旧门控左界 `248` 之外）。

> 顺带澄清一条**不修**的：头部长度本身没有按箭杆长度夹（拖 10pt、线宽 30 会得到一个
> 远超所拖长度的巨大三角头）。那是**设计取舍**、不是缺陷 —— 而箭杆画反是缺陷，已修。

### 2.6 ⌘Q / 「退出 AISnap」不走关闭确认，标注静默丢失（既有问题｜独立评审发现）

`d71f784` 补的关闭确认只覆盖标题栏 X 与工具栏「放弃」；`AppDelegate` 没有
`applicationShouldTerminate`，按 ⌘Q 直接退出。**数据丢失的口子留一个就等于没堵。**

**修复**：实现 `applicationShouldTerminate`，复用同一个 `confirmDiscardIfNeeded()`
（确认逻辑保持单一来源）。探针守的是**接线**与"没有标注窗口时直接放行"；
"有未保存标注会拦下来"复用同一函数，行为由既有的 `windowShouldClose` 断言覆盖。

## 三、`build.sh --install`（`cc5702c`）的两处加固

1. **不是原子操作**：原来"先 `rm -rf` 旧包、再 `cp`"。`cp` 中途失败会留下装了一半的包，
   而旧版本已经删了 —— 用户手上就没有能用的应用了。改为先拷到 `$TARGET.new`、
   **成功之后**才换包；拷贝失败等于什么都没发生。
2. **不提醒应用正在运行**：换掉磁盘上的包不会换掉已经在跑的进程，
   用户会觉得"装完了怎么没变化"。现在会打印提醒。

端到端实测（`INSTALL_DIR=/tmp/fakeapps`，**不碰真的 /Applications**）：

| 断言 | 结果 |
|---|---|
| 没有留下 `.new` 暂存目录 | ✅ |
| 旧版本（记号文件）已删除 | ✅ |
| 新包可执行文件就位 | ✅ |
| 新包 `codesign --verify --strict` 通过 | ✅ |
| 真的 `/Applications` 未被改动 | ✅ |
| "应用正在运行"提醒确实打出来了 | ✅ |
| 测试用的 LaunchServices 注册已清除 | ✅ |

## 四、窗口挑选：`layer == 0` 过滤过宽（`833b024` 引入｜独立评审发现）

只认 `layer == 0` 会把**浮动面板 / 画中画**（`NSFloatingWindowLevel` = 3 等）静默跳过，
于是截到它**后面**那个窗口 —— 用户点的明明是浮窗，拿到的却是别的东西，
比"没反应"更难察觉。

实测（合成窗口列表，Z 序：浮层在前）：旧过滤返回 `[2]`（后面那个普通窗口），
新过滤返回 `[1, 2]`（浮层在前）—— **判别力已验证**。

**修复**：判据改为 `0 <= layer < 20`，保留 Z 序。
- 该范围既含普通窗口也含浮层；
- `layer >= 20` 是系统 UI（程序坞 20、菜单栏 24、Window Server 覆盖层 2147483630），
  `layer < 0` 是通知中心 —— 这些才是该挡掉的。

> **一个差点犯的错**：第一版把 `layer == 0` 单独提到前面做"两档"。那等于**放弃 Z 序**，
> 浮窗在普通窗口前面时反而会去截后面那个 —— 正是要修的那个 bug。Z 序本身就是正确答案，
> 只需要把系统层滤掉。

## 五、探针环境：`~/Library/Preferences/run.plist` 会跨次污染（独立评审发现）

会构造真实 `AnnotationWindow` 的探针走的是 `Preferences.shared`（= `UserDefaults.standard`），
而探针二进制的文件名是 `run` —— 偏好于是落进 `~/Library/Preferences/run.plist`。
`run_all.sh` 原来只清 `com.aisnap.probe.*`，扫不到它。实测里面留着：

```
colorHex = "#0000FF"   lastToolTag = 11   lineWidth = 30
updateFeedURL = ""     watermarkText = "机密-请勿外传"
```

其中 `updateFeedURL = ""` 会让**后续探针**读到 `configuredFeedURL == nil`，行为与预期不符
（独立评审第一次跑端到端更新探针就被它绊住）。**修复**：`run_all.sh` 的清理段一并删掉它。

## 七、仍未验证的怀疑

1. **权限被拒时的多候选重试**（`Sources/ScreenCapture.swift`）：候选循环会对每个候选各跑
   一遍失败的 SCK，而不是见到 `.permissionDenied` 立即抛出。需要「TCC 被拒 + 鼠标下有真实
   窗口」的环境才能量化，未复现。真要修就是在循环里对权限类错误短路。
2. `exportPixelSize` 最后的兜底 `baseImage.size * 2` 是**猜** 2×；找不到可达路径。
3. `latest.json` 的版本号目前没有构建期校验与应用版本绑定。**刻意不加**：两次发行之间
   开发时把 `VERSION` 提前调高是正常做法，那时 `latest.json` 理应仍指向**上一个已发布版本** ——
   硬校验两者相等会把正常的开发流程卡住。这件事由 `scripts/release.sh` 的顺序来保证
   （它会把三处一起改），而不是靠构建期断言。

> 另：`CGContext(data: &buffer, …)` 把数组指针交给会继续持有它的 CGContext（`&array` 只在
> 调用期间保证有效，书面 UB）—— **已随 2.3 的修复删除**（那段像素探测整段去掉了）。
