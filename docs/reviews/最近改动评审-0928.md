## 二、确认的缺陷（已修复）

### 2.1 短箭头的箭杆被画到**起点的反方向**（`d71f784` 引入）

`Sources/Models.swift` 的 `drawArrow` 里，实心头部的箭杆回缩量取 `headLength * 0.85`，
而 `headLength = max(style.headLength, lineWidth * 3.2)` 在线宽 15 时是 **48** —— 回缩 **40.8pt**。

于是**任何比 40.8pt 短的箭头**，`endPoint - 回缩量` 落到起点**反方向**去，箭杆倒着画出来，
在三角形头后面露出一截圆头。箭头的头部本来就是随线宽放大的（这正是 `d71f784` 干的事），
所以线宽越大越容易撞上。

像素实测（`master_parity_probe` 第 2 节，2x 画布）：

| 箭头 | 实测最左墨迹 | 几何容许的最左 | 结论 |
|---|---|---|---|
| 短箭头 20pt | 443 | 456.9 | ❌ 多出 14px —— 箭杆越过起点 |
| 长箭头 350pt（**对照**） | 85 | 85.0 | ✅ 完全吻合 |

对照组是必须的：少了它，一个"干脆不画箭杆"的假修复也能让短箭头那条断言通过。

**判别力**：把修复退回旧写法，**恰好只有**「短箭头」那条失败，长箭头对照仍通过。

**修复**：回缩量加"不超过箭杆本身长度"的上限；整根箭杆都藏在头部里时干脆不画箭杆。

### 2.2 restyle 的重做（⇧⌘Z）**完全失效**（`833b024` 引入）

`Sources/AnnotationView+UndoRedo.swift` 的 `undo()` 分支，在**已经把颜色改回旧值之后**
才去读 `obj.color` 来构造 redo 记录：

```swift
obj.color = oldColor
if let width = oldLineWidth { AnnotationView.setLineWidth(width, on: obj) }
redoStack.append(.restyle(colorKey: colorKey,
                          oldColor: oldColor, newColor: obj.color,          // ← 读到的已经是旧值
                          oldLineWidth: oldLineWidth,
                          newLineWidth: AnnotationView.lineWidth(of: obj))) // ← 同上
```

redo 记录里 `newColor == oldColor`、`newLineWidth == oldLineWidth`，重做成了空操作。

实测（选中矩形 → 换蓝 → 线宽改 24 → 撤销×2 → 重做×2）：

| 步骤 | 期望 | 实测（修复前） |
|---|---|---|
| 重做换色 | 蓝 1.00 | 蓝 **0.24**（还是红） ❌ |
| 重做改线宽 | 24 | **8** ❌ |

**判别力**：退回这一处后**恰好只有**这两条新断言失败，原有的 5 条 restyle 断言**仍全绿**。

也就是说 —— **原来的探针根本抓不到它**：第 8 节只测了撤销方向，**从没测过重做方向**。

**修复**：redo 记录原样沿用传进来的 `newColor` / `newLineWidth`。

**不是系统性问题**：同文件里 `.move` / `.rotate` / `.scale` 都从绑定参数构造记录，
`.editText` 先 `let current = shape.text` 再改（模式本来是对的）—— 只有 `.restyle` 写反了。

## 三、`build.sh --install`（`cc5702c`）的两处加固

`--install` 本身的设计（`rm -rf` 而不是丢废纸篓）是对的，证据也在提交信息里。
但这段破坏性逻辑有两处可以更好：

1. **不是原子操作。** 原来是「先 `rm -rf` 旧包 → 再 `cp -R`」。`cp` 中途失败
   （磁盘满、被中断）会留下一个装了一半的包，而旧版本**已经删了** ——
   用户手上就没有能用的应用了。改成：先拷到 `$TARGET.new`，**成功之后**才换掉旧包。
   现在拷贝失败等于什么都没发生。
2. **不提醒应用正在运行。** 换掉磁盘上的包不会换掉已经在跑的那个进程，
   用户会觉得"装完了怎么没变化"。现在会打印一条提醒。

端到端实测（`INSTALL_DIR=/tmp/fakeapps`，**不碰真的 /Applications**）：

```
已拷贝到临时位置：/tmp/fakeapps/AISnap.app.new
已删除旧版本：/tmp/fakeapps/AISnap.app
已安装：/tmp/fakeapps/AISnap.app
⚠️  AISnap 正在运行：请完全退出后重新启动，新版才会生效（旧进程仍跑旧代码）
已刷新 LaunchServices 注册
```

| 断言 | 结果 |
|---|---|
| 没有留下 `.new` 暂存目录 | ✅ |
| 旧版本（记号文件）已删除 | ✅ |
| 新包可执行文件就位 | ✅ |
| 新包 `codesign --verify --strict` 通过 | ✅ |
| 真的 `/Applications` 未被改动（仍是 `20260928.1044`） | ✅ |
| 测试用的 LaunchServices 注册已清除 | ✅ |

## 五、未能验证的怀疑（**需要你在特定环境下确认**）

### 5.1 `canCaptureRealPixels()` 可能把"没有权限"判成"有权限"（优先确认）

`Sources/AppDelegate.swift`（`833b024`）在 `CGPreflightScreenCaptureAccess()` 返回 false 时，
用一张 **2×2 截图**探测兜底，判据是**有没有 alpha ≠ 0 的像素**。

问题在于：**没有屏幕录制权限时，`CGWindowListCreateImage` 并不一定返回 nil** ——
有大量报告说它返回的是**只有桌面壁纸**的图：**非 nil，而且壁纸是不透明的**。
若属实，这个兜底在真正没权限的机器上会返回 true，于是：

- 应用**不再弹权限引导**（`checkScreenCapturePermission()` 直接返回 true）；
- 用户截图得到的是壁纸 / 黑图，而且**没有任何解释**。

这比它想修的那个问题（授权后仍被判无权限）**更难排查**，所以值得先确认。

先例本身是**互相矛盾**的，这正是它必须实测的原因：

- [screenpipe 的同类修复](https://github.com/screenpipe/screenpipe/commit/ca47af39107e625447528c19765860afeb2c1a11)
  断言"内核要么给图、要么给 `NULL`"，并按 **nil 与否**判定（**不是**按像素内容）；
- 而 [Stack Overflow 上这条](https://stackoverflow.com/questions/58997582) 的标题恰恰是
  "Capture screen with CGWindowListCreateImage just **return the wallpaper**"；
- [MaaTools 的 PR](https://github.com/viatearz/MaaTools/pull/1) 说的是"返回**空白帧**"。

三种说法对应三种行为，而我们的实现只在其中两种下正确：

| 无权限时的真实行为 | 我们的实现 |
|---|---|
| 返回 `nil` | ✅ 判为无权限 |
| 返回**透明**空白帧 | ✅ 判为无权限 |
| 返回**壁纸**（不透明） | ❌ **误判为有权限** |

**本机验不了**：这个会话里所有进程都已经持有屏幕录制授权 ——
探针跑出来 `preflight=true`，兜底分支**根本不会被执行**。
（不能用 `tccutil reset ScreenCapture` 去造这个场景：那会把你环境的授权一起清掉。）

**验证方法**（一台 AISnap 从未被授权过的机器，或）：

```bash
tccutil reset ScreenCapture com.aisnap.app
# 启动 AISnap 触发截图，观察是否弹出权限引导；若没弹且截出壁纸/黑图 → 命中
```

**要修的话**，方向不是"再调一个阈值"（像素内容本身无法区分"别的应用的窗口"和"壁纸"），
而是换一个**权限专属的信号**：`SCShareableContent.current` 在缺权限时会报错
（`userDeclined`），而应用本来就依赖 ScreenCaptureKit 截图。

### 5.2 `windowCandidates` 的 `layer == 0` 过滤会连带排除浮动窗口（影响较小）

浮动面板 / 画中画这类窗口的 `CGWindowLayer` 是 3 等非 0 值，会被一并排除。

实测本机当前屏幕上的非 0 层只有：Window Server 覆盖层（`2147483630`、`24`＝菜单栏）、
程序坞（`20`）、通知中心（负数）—— **过滤掉的正是该过滤的**（菜单栏 24 与铺满全屏的
程序坞 20 正是 `833b024` 修掉的那个 bug 的根源）。所以这条目前只是**理论上的收窄**，
没有观察到真实受害窗口。

若将来真的咬人，稳妥做法是**分层退让**：先按 `layer == 0` 挑，挑不到再退回"任意层"，
而不是直接判失败。
