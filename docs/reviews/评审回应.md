### P1 · 「V4 是悬着的最大未爆弹」 → **已被实测证伪**

评审的推理是：

> `captureImage(in:)` 没有 configuration 参数，只能用默认 `SCStreamConfiguration`
> —— 也就是默认 width/height（1920×1080）生效的那一套……**极可能输出非 Retina 甚至固定 1080p**

推理链条本身合理，但实测结果相反：

```
整屏：(0, 0, 2560, 1080) 点 → 5120x2160 px
推算缩放比 = 2.00x
```

`5120 / 2560 = 2.00`、`2160 / 1080 = 2.00` —— **精确等于显示器的 backing scale**。

结论：`captureImage(in:)` **会按 `rect × 显示器 scale` 自行计算输出分辨率**，
不走 `SCStreamConfiguration` 的默认 width/height（那个默认值只在显式构造
configuration 并传给 filter 路径时才起作用）。

**所以不需要砍掉 in-rect 路径，也不存在 1080p 降级问题。**

> 这条值得记下来：`SCStreamConfiguration.width/height` 的 1920×1080 默认值
> 只影响 **filter 路径**；in-rect 路径是独立实现，不受影响。

## 二、已修复的发现

### P2-1 · 副屏 Y 翻转 bug → **已修复**（`b26f005`）

评审说「请把它记在账上」。核对后确认是**真 bug**，直接修了：

`windowIDUnderMouse()` 与 `finishSelection()` 都用 `NSScreen.main` 的高度做全局 Y 翻转。
而 `NSScreen.main` 的定义是「当前 key window 所在屏，无 key window 时为菜单栏所在屏」——
**标注窗口开在副屏时取值会变**，翻转基准随之出错，鼠标在副屏时命中到错误的窗口。

正确基准是**主显示器**（Quartz 原点所在、`frame.origin == .zero` 的那块）的高度：

```
AppKit 全局原点在主显示器左下、Quartz 全局原点在主显示器左上
⇒ quartzY = 主显示器高度 − appKitY   （对所有屏幕都成立）
```

新增 `ScreenCapture.primaryScreenHeight` 作为单一来源，两处统一使用。
顺带把翻转计算从循环内提到循环外（整个循环共用一个点，没必要每次重算）。

> 自检输出正好反向印证了这一点：AppKit `#1 = (-803, -982, …)` ↔ Quartz `(-803, 1080, …)`，
> `1080 − (−982 + 982) = 1080`，而 1080 正是主显示器高度。
