## 二、对审计结论的一处更正

审计 2.3 写道：

> `colorFromKey` 用 `NSColor(red:green:blue:)`（**Generic/Calibrated RGB 空间**）生成 ID 色

**实测更正：不是 Generic RGB，是 sRGB。**

```
NSColor(red:green:blue:).cgColor            → kCGColorSpaceSRGB
CGColor(colorSpace: DeviceRGB, ...)         → kCGColorSpaceDeviceRGB
NSColor(cgColor: DeviceRGB色).cgColor        → kCGColorSpaceDeviceRGB
```

（现代 macOS 上 `NSColor(red:green:blue:alpha:)` 落在 sRGB，不再用 Generic RGB。

**但审计的核心担忧完全成立**：sRGB ≠ DeviceRGB，中间仍有一次色彩空间转换；
显示器的色彩配置偏离 sRGB 时，转换就可能让分量偏移 ±1 → 精确值字典查找静默失败。
所以「加固为构造性正确」的建议是对的，只是空间名需要更正。

顺带确认了最小改法可行：`NSColor(cgColor: DeviceRGB色).cgColor` **能保住 DeviceRGB 空间**，
所以不必动 `AnnotationObject` 协议（不必把 `NSColor` 全面换成 `CGColor`）。

## 四、已修复

### 4.1 虚线与点线实际渲染为实线（审计 2.2）→ `13e6bba`

**根因**：`Arrow.drawArrow` 固定用 `[8, 4]` 的 dash，同时设了圆头 `.round`。
圆头让每段 dash 两端各外扩 `lineWidth / 2`，实际覆盖长度 = `dash + lineWidth`。
线宽取默认值 **15** 时：`8 + 15 = 23 > 周期 12` → 相邻 dash 完全重叠 → 实线。

**修复**（按审计建议，两处一起改）：

| 层 | 改动 |
|----|------|
| 视觉层 | 抽出 `applyLineStyle(_:lineWidth:in:)`，dash 随线宽缩放；虚线用 `.butt` + `[3w, 2w]`；点线用 `.round` + `[1, 2w]` |
| picking 层 | `drawArrow` 新增 `forceSolid` 参数，`drawHitTest` 传 `true` |

**为什么必须一起改**：只修视觉的话，虚线箭头会真的出现空隙，
点击落在空隙上就选不中该对象 —— 命中区破损。业界标准也是 picking pass 永不继承 dash。

**修复后行为**：视觉有真实间隙（40%），命中区仍是实线（0 空隙，可整段点中），
即**用户看到虚线、仍能点中整条线** —— 两个目标同时满足。

### 4.2 ID 色色彩空间加固（审计 2.3）→ `6f6cd93`

`HitTestBuffer` 现在持有 `colorSpace` 属性（与位图共用同一个 DeviceRGB 空间），
`colorFromKey` 用 `CGColor(colorSpace:components:)` 直构后再包成 `NSColor`。

`colorFromKey` 由 `static` 改为实例方法 —— 全局只有一处调用点，改动面极小。

## 五、暂缓项

### 5.1 拖拽时全量重绘（审计 2.5）→ **决定不处理**（已实测关闭）

**决定**：不处理。理由不是「估计够用」，而是实测出的成本结构不支持这个优化方向。

先纠正一个前提：缓冲区尺寸是**逻辑点**而非像素 —— `NSImage(cgImage:size:logicalSize)`
使得 `image.size` 为 2560×1080 点，故 `HitTestBuffer` 是 2560×1080 而非 5120×2160。
（附带结论：Layer B 是 1x 分辨率，这对 picking 足够 —— 精度损失 1 点不可感知，
内存从 42MB 降到 10MB。）

**实测（2560×1080，`drag_perf_probe.swift`）：**

| 操作 | 成本 |
|---|---|
| 整画布 fill（`clear()` 的全部代价） | 0.15 ms |
| 10 个对象描线+填充 | 0.25 ms |
| **`redrawAll`（10 对象）** | **0.37 ms** |
| `redrawAll`（50 对象） | 1.32 ms |
| `redrawAll`（200 对象） | 4.88 ms |

对象数从 10 增到 200（20 倍），成本只增到 4.88ms —— **仍然在 60Hz 帧预算内**。
审计原话是「≤50 无感，数百对象掉帧」：前半句实测支持，**后半句不成立** ——
200 个对象也只有 4.88ms。即"数百对象掉帧"的门槛比审计估计的高。

> 探针里的模拟对象是**整条画布对角线**的描线，比真实标注（多为局部小图形）
> 覆盖的像素更多，因此上表每对象增量（约 0.024ms）是**偏保守**的上界。

**但补测发现同一热路径上有个大得多的固定成本，且与对象数完全无关：**

| 操作 | 成本 | 倍率 |
|---|---|---|
| `redrawAll`（10 对象） | 0.37 ms | 1× |
| **`debugVisualization`（调试面板）** | **10.92 ms** | **30×** |
| 对照：同尺寸**裸 CGContext** 做同样的事 | 0.37 ms | 1× |

成因在 `NSImage.lockFocus` 这条路径上，而非绘制本身：
`lockFocus`/`unlockFocus` **空转**就要 3.86ms，加上全画布 fill 后到 7.51ms，
再加 10 个对象即 10.92ms。**同样的操作在裸 `CGContext` 上只要 0.37ms —— 差 29 倍。**

而 `refreshDebugView()` 只要 `debugImageView != nil` 就会执行，调试面板又是常驻的，
所以 `mouseDragged` 的三个分支（moving / rotating / scaling）每帧都在跑它：

```
单次拖拽事件 ≈ redrawAll(0.37) + debugVisualization(10.92) ≈ 11.3 ms
120Hz 帧预算 8.33ms → 已超；60Hz 16.7ms → 占 68%（叠加 Layer A 绘制后可能丢帧）
```

**结论：审计 2.5 优化的是成本里的次要项。** 正确的收口不是改 `redrawAll`，
而是把调试面板移出热路径。三个做法（成本从低到高）：

1. **`refreshDebugView` 加可见性门控** —— 面板不可见时直接 return（一行）
2. **`debugVisualization` 改用裸 `CGContext` + `NSImage(cgImage:)`** —— 10.92ms → 约 0.4ms
3. **彻底移除调试面板** —— 同时释放约一半的工具栏宽度，
   解掉 M1-4 / M1-5 因工具栏溢出而阻塞的问题（见开发计划）

三者不互斥，1+2 是纯收益且保留开发期工具；3 另外解决了另一个已记录的问题。

**顺带排查（未复现问题）**：`compositeImage()` 用的是同一种 `NSImage.lockFocus`
写法，一度怀疑它会把 Retina 截图降成 1x。离屏实测产物为
`5120×2160 px (NSCGImageSnapshotRep)` —— **保住了 Retina，无此问题**。
（探针进程无窗口服务器，backing scale 取值可能与真机不同，如需确证可在
运行中的应用里导出一次并核对像素尺寸。）
