### 2.2 数字键范围写错了

报告写「键盘闭环 Enter/⌘C/⌘S/Tab/**1–7**/Esc/Delete」。实际 `AnnotationView.swift:576-580`：

```swift
// 数字键 1..9 → 直接选中第 N 个绘图工具
if let chars = event.charactersIgnoringModifiers,
   let digit = Int(chars), digit >= 1, digit <= 9 {
```

是 **1–9**。而绘图工具已有 **12 个** —— 所以第 10–12 个工具（模糊、橡皮、取色）**无法用数字键直选**。这不是 bug，但是个体验缺口，且报告没提。

## 三、报告里我认同的规划建议

### 3.1 「手感层」这个角度比我之前的思路更准 ★

报告列：方向键 ±1px 微调选区 · 延时截屏 · 选区时窗口吸附高亮 · 直线/画笔/记号笔
（合计 3–4 天），理由是「这些是 Snipaste **免费版**用户的肌肉记忆，缺一项就少一个『设为默认』的理由」。

我上一轮排优先级时是按「功能清单还剩哪些」在排，而这个角度直接对准**阶段一的验收标准**
（能否连续一周设成默认）。**这个判断比我原来的更贴近目标。**

其中「选区时窗口吸附高亮」报告给了实现路径：用**冻结帧 + 冻结时刻的 CGWindowList 边界**，
不需要实时捕获 —— 这与「先冻屏再选区」的现有架构天然契合，成本比看上去低。

### 3.2 「把截图后动作数据化」值得排在「语义理解」之前 ★

报告指出：取色 / OCR / 脱敏 / 贴图 / 复制 / 上传本质都是 `CaptureRequest → [ExportTask]`。
**现在立起来成本最低**（动作还少），而它是阶段三「工作流 + 插件系统」的地基。

我认同，并且认为它**应该优先于「语义理解」** —— 后者是加一个功能，
前者是决定后面所有功能怎么加。等动作长到十几个再抽象，代价会高一个数量级。

### 3.3 其余建议的排序我也认同

真签名公证（唯一分发阻塞）> 智能脱敏（地基已就位）> 手感层 > 语义理解 > Pin 鼠标穿透。
商业化的判断（免费线 = Snipaste 免费版水平 + 二次编辑，已超；Pro = AI 线）与我的判断一致。

## 四、我建议的实际顺序（与报告的差异）

报告把签名排第 1。我同意它对「可分发」的意义，但**它依赖外部审批周期**，
不该阻塞可并行的开发。所以：

1. **补齐两个漏项**（各半天）：序号可重排 + 贴图鼠标穿透 —— 它们是「路线图要求但漏做」，
   先还清比开新战线干净，且都是小改动
2. **手感层**（3–4 天）：方向键微调 → 延时截屏 → 选区窗口吸附高亮（用冻结帧边界）
3. **签名公证**：**并行推进**（申请账号是等待时间，不是工作时间）
4. **`CaptureRequest → [ExportTask]` 模型**：在动手做「智能脱敏」**之前**立起来，
   这样脱敏就是它的第一个 `ExportTask` 实现，而不是又一个特例
5. 智能脱敏 → 语义理解
